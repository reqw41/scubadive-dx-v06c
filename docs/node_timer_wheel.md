# Узел «колесо таймеров»: постановка (НЕ РЕАЛИЗОВАН)

Очередь: после основных узлов сметы скорости. Документ написан заранее, чтобы
условия корректности не пришлось восстанавливать по памяти.

## Что предлагается

Сейчас тик обходит все записи объектов и **декрементирует счётчик в поле `+0x0F`**
у каждой. Замер: из 81 сканируемой записи за тик счётчик реально досчитывает до
нуля только **2.26 раза** — то есть **97% скана это холостой декремент**.

Идея: заменить «декремент у всех» на колесо таймеров — очередь по моменту
срабатывания, где за тик трогаются только те записи, чей срок настал.

## Почему это НЕ повторение опровергнутого live-list

Опровергнутая идея (см. доклад по разведке) — скан только по «живым»: она
самоубийственна, потому что не просканированная запись не тикает счётчиком,
`LB737` для неё не зовётся, бит видимости не пересчитывается, и запись не
возвращается в список никогда. Список может только пустеть.

Колесо таймеров этим не страдает: запись не выпадает из структуры, а
перепланируется на будущий тик. Каждая запись по-прежнему получает обработку —
просто не каждый тик, а ровно тогда, когда её счётчик и так дошёл бы до нуля.

## УСЛОВИЯ КОРРЕКТНОСТИ — записать в реализацию как требования

Эти три пункта выявлены разведкой и являются причиной, по которой узел вынесен
отдельно, а не сделан заодно с F.1/F.2.

### 1. Побайтный ПОРЯДОК обработки менять нельзя

Два наблюдаемых эффекта зависят от того, в каком порядке записи доходят до
`LB737`:

* **выделение буферов `LB676` идёт по принципу «первый свободный»** — переставь
  порядок, и объекты получат другие буферы;
* **`RANDOM` расходуется по порядку массива** — каждый бросок сдвигает поток, и
  другой порядок обращений даёт другую игру.

Значит колесо обязано выдавать записи в тот же относительный порядок, что и
линейный обход. Практически это означает: в пределах одного тика срабатывания
должны обходиться по возрастанию индекса записи, а не по порядку попадания в
корзину.

### 2. Период `+0x0E` меняется на ходу

Перепланирование нельзя считать один раз при постановке в корзину: `LB737` может
изменить период у той же записи, и следующий срок обязан считаться от НОВОГО
значения. То есть корзина заполняется при срабатывании, а не заранее на весь
цикл.

### 3. Пустых записей не бывает

Проверять «жива ли запись» не надо и НЕЛЬЗЯ: тела `LB737`/`LB7BB` не проверяют
ни одного поля на ноль и не имеют раннего выхода, а `InitLevelVars` строит ровно
столько объектов, сколько указано в счётчике группы. Любая проверка «на пустоту»
будет проверкой, которая всегда ложна, — то есть чистой тратой тактов.

## Смета — считать при реализации

Сравнивать надо не с нулём, а с УЖЕ ДОЖАТЫМ линейным обходом: после этапов F.1 и
F.2 тело стоит **45 тактов на запись** (было 76 и 145). При 81 записи за тик это
3645 тактов. Колесо должно уложиться заметно ниже с учётом:

* цены перепланирования на каждом срабатывании (2.26 раз за тик),
* цены поддержания порядка по индексу внутри тика,
* байтов на структуру (корзины на глубину периода) — периоды надо сначала
  замерить, гистограммой по прогону.

Порог принятия тот же, что у остальных узлов: **не меньше 1% такта при разумной
цене**, замер темпа и полный набор гейтов после узла.

## Что померить ПЕРЕД реализацией

1. Гистограмма значений периода `+0x0E` по группам и уровням — от неё зависит
   глубина колеса и вообще применимость схемы.
2. Доля записей, у которых `LB737` меняет период — если она велика, выигрыш
   съедается перепланированием.
3. Проверка на замере, что порядок обращений к `RANDOM` при колесе совпадает с
   линейным: это прямой гейт (последовательность значений `RANDOM` за прогон
   обязана совпасть байт в байт), и он же ловит нарушение пункта 1.

# ЗАМЕРЫ ПЕРЕД РЕАЛИЗАЦИЕЙ (сделаны, числа окончательные)

## 1. Условие «период меняется на ходу» — ПУСТОЕ

Замер: уровень 4, 1502 тика, группа I из 51 записи. Сторож записи повешен на поля
`+0x0E` всех записей группы, счёт ведётся только во время исполнения `LB737`.

    срабатываний LB737 ................. 4558 (3.03 на тик)
    из них МЕНЯЮТ период +0x0E .......... 0 (0.0%)

Ноль из 4558. Значит **срок считается один раз при постановке в корзину** и
перепланировать на каждом срабатывании не нужно. Одно из трёх условий
корректности из постановки снято замером.

Периоды при этом разнообразны: 42 различных значения в диапазоне **31..125**.
Отсюда глубина колеса — 128 корзин (степень двойки, индекс = такт & 127).

## 2. Порядок ВНУТРИ тика наблюдаем — сортированная вставка ОБЯЗАТЕЛЬНА

Замер: уровень 4, 3001 тик, считаются срабатывания `LB737` в пределах одного тика.

    срабатываний всего .................. 7961 = 2.65 на тик
    распределение по тикам:
      0:388  1:716  2:779  3:510  4:286  5:157  6:99  7:41  8:13  9:5  10:2  11:2
      плюс два выброса: 574 и 582 срабатывания в одном тике
    тиков с БОЛЕЕ ЧЕМ ОДНИМ срабатыванием ... 1896 из 3000 = 63.2%

**Шестьдесят три процента тиков имеют больше одного срабатывания.** Значит
относительный порядок этих записей наблюдаем всегда, а не изредка: он определяет,
кто первым возьмёт буфер из пула («первый свободный») и кто первым израсходует
`RANDOM`. Вставка в корзину обязана быть **сортированной по индексу записи**.

Хорошая новость: средняя населённость корзины равна средней частоте срабатываний,
то есть **около 2.65 записи**. Сортированная вставка проходит по списку из двух-трёх
элементов — это дёшево, а не страшно.

**Два выброса (574 и 582 срабатывания в одном тике) — это инициализация уровня и
пере-спавн.** Массовая постановка в корзины должна идти отдельным путём: не через
сортированную вставку по одной, а сразу списком, иначе она станет квадратичной.

## 3. Место — забронировано и охраняется

Данные колеса живут в `$BD00..$BFFF` (три верхние страницы пула буферов):

    128 голов корзин по 2 байта ......... 256 Б
    связки по индексу записи, 208 x 2 ... 416 Б
    итого ............................... 672 из 768, запас 96 Б

Бронь сделана в `b5653af` (бит 7 в таблице `LB676`, распределитель уважает её
своей же логикой), сторож в `787e26c` (порог 11 рабочих страниц из 13, три
негативных контроля).

## Смета

Линейный скан после этапов F.1/F.2 стоит **45 тактов на запись**, записей 81 за
тик — это **3645 тактов на тик = 8.9%** такта. Перепланирование при 2.65
срабатываниях на тик и сортированной вставке в список из ~3 элементов обойдётся
примерно в 150 тактов на тик. **Чистый выигрыш до ~8.5%.**

## Что осталось сделать

Реализация не начата сознательно: она трогает самые горячие циклы игры
(`LBEA2`, `LBE48`, `LC439`/`LC44C`), и полуфабрикат в них хуже, чем его отсутствие.
Порядок работ:

1. глобальная нумерация записей поверх пяти групп с разными шагами (21/26/26/26/28)
   и обратное отображение индекс → адрес записи;
2. постановка всех записей в корзины при инициализации уровня — массовым путём;
3. замена пяти циклов скана на обход одной корзины `такт & 127`;
4. сортированная вставка по индексу при перепланировании;
5. **lockstep после каждого осмысленного шага** — он ловит расхождение поведения,
   а гейт только картинку; здесь важно именно поведение.

# ЗАКРЫТО: КОЛЕСО НЕПРИМЕНИМО

**Причина не в байтах и не в тактах. У игры нет единого порядка обхода записей,
а корзина хранит один список с одним порядком.**

## Что убило конструкцию

Колесо обязано сохранять относительный порядок записей, срабатывающих в одном
тике: он решает, кто первым возьмёт буфер из пула («первый свободный») и кто
первым израсходует `RANDOM`. Замер показал, что этот порядок наблюдаем почти
всегда — **63.2% тиков имеют больше одного срабатывания**.

А сам порядок обхода в игре НЕ ПОСТОЯНЕН: набор обходчиков и их
последовательность выбирает `LBDBA` по строке мини-карты.

    поверхность .... LBE40 (группа II), затем LBE9A (группа I)
    глубина ........ LC431 (группы IV и V)

При этом адресный порядок групп ИНОЙ: I `0x79D3` < II `0x7E02` < III `0x810E`
< IV `0x8622`. То есть на поверхности группа II обходится РАНЬШЕ группы I, хотя
лежит по большему адресу. Сравнение адресов вместо индексов (дешёвое упрощение,
экономившее 416 байт таблицы) не годится.

Один глобальный индекс не может быть верным сразу для всех сцен: индекс один, а
порядков несколько.

## Три обхода, все отвергнуты

1. **Отдельное колесо на каждую комбинацию групп** — умножает 672 байта на число
   комбинаций. Места нет: забронировано 768.
2. **Пересортировка корзин при смене сцены** — смена происходит при каждом
   пересечении границы по глубине, то есть постоянно. Дороже самого скана.
3. **Хранить ключ сортировки и сортировать при срабатывании** — при 63%
   многосрабатывательных тиков это сортировка почти каждый тик.

## Что при этом проверено и осталось верным

Два из трёх условий корректности замером сняты и к конструкции претензий не имели:

* период на ходу не меняется — **0 из 4558** срабатываний;
* вставка дешёвая — средняя населённость корзины **2.65**.

Убило третье: порядок. Оно оказалось не краевым случаем, а нормой.

## Смежное направление — тоже пустое

Возникла идея «не сканировать группы, неактивные в текущей сцене». Замер профилем
показал, что экономить нечего: `LBDBA` уже зовёт только активных обходчиков.

    уровень 4, поверхность: LBEA2_adv 1646 + LBEA2 1350
                            + LBE48_adv 1696 + LBE48 1335 = 6027 тактов/тик
                            (LC431 не исполняется вовсе)
    уровень 4, глубина:     LC431..LC45C = 4938 тактов/тик

Попутно уточняется смета самого колеса: цена скана была не 3645 тактов на тик, а
**6027 на поверхности** (14.8% такта). Приз был даже больше заявленного — но взять
его этой конструкцией нельзя.
